- **Accounting pivot:** invoice posts to `customer_ledger` at DISPATCH (debit = full total_amount). Pre-dispatch = edit orders directly; post-dispatch = debit/credit notes only. The posting logic itself lives in ONE shared helper, `postCreditOrderDispatchAccounting()` (core/functions/helpers.php, added 4 Aug 2026) — journal (AR debit/Revenue credit + Other-Sales COGS lines) + customer_ledger row + invoice_snapshot, idempotent (no-ops if a journal already exists for the order). Called from `cr/credit_dispatch.php` (the real dispatch flow) AND `cr/admin_edit.php` (whenever an edit moves status into goods_on_board/shipped/delivered) — added the latter after finding 7 real orders that had been shipped/delivered via Admin Edit's raw status field with ZERO accounting posted (see backlog for the full incident). Any FUTURE code path that can move an order into a shipped-equivalent status should call this same helper rather than reimplementing the posting logic — that's exactly the mistake that caused this bug.
- **Balance invariant:** `balance_due = total_amount − advance_paid − amount_paid` (advance and allocated payments are separate columns; recomputes must subtract both).
- **Customer true outstanding:** `initial_due + ledger debits − credits` via `getCustomerOutstanding()` — never trust `customers.current_balance`.
- **credit_order_workflow timestamp column is `performed_at`, NOT created_at.**

- **COUNT(*)-based sequence-number gotcha:** several document-number generators in this codebase pick the next number as `COUNT(*)+1` (rows of this type/year) rather than `MAX(existing sequence)+1`. This looks fine until any row of that type/year is ever cancelled/deleted/rolled back — the live COUNT drops below the highest number actually issued, and the generator starts reissuing an already-used number, hitting the table's UNIQUE constraint. Confirmed as a real, live bug (not theoretical) in `Purchaseadnanmanager.php`'s `generateNoteNumber()` (DAN/CAN adjustment notes) — fixed 3 Aug 2026 to the same `SELECT ... ORDER BY id DESC LIMIT 1` + extract-and-increment pattern already used correctly by `generatePONumber()` in the same file, `cr/create_order.php`'s order-number generation ("Bug 4 fix"), and `trading/commodity_sale.php`'s sale-number generation. **Any other `COUNT(*)... as cnt`-style number generator found in this codebase should be treated as suspect and checked** — the safe pattern is always MAX-existing-sequence, never a live row count.
- **DDL implicit-commit gotcha:** MySQL auto-commits any open transaction on CREATE TABLE / ALTER — so every `ensure*Table()` helper PROBES first (SELECT/information_schema) and only runs DDL when truly missing; ALWAYS call ensure* helpers BEFORE beginTransaction. This bug surfaced as "There is no active transaction" when saving privileges.

- **CRITICAL, app-wide bug found + fixed 29 Jul 2026 — `AuditLogger::ensureTable()` was silently ending transactions system-wide.** It ran `CREATE TABLE IF NOT EXISTS system_audit_log` **unconditionally on every request's first `auditLog()` call**, guarded only by a per-request `static $done` flag — NOT a probe-first check. MySQL implicit-commits any open transaction on DDL even when the table already exists (the same class of bug as the `ensure*Table()` gotcha already documented above), so **any `auditLog()` call made from inside a `beginTransaction()`/`commit()` block, anywhere in the app, silently ended that transaction early** — the money-moving writes already inside it would still land (since the implicit commit commits everything so far), but the subsequent explicit `$db->commit()` then throws "There is no active transaction" (uncaught, since `Database::commit()`/`beginTransaction()`/`rollback()` are raw proxies with no try/catch), aborting the request with an error even though the core writes had actually gone through moments earlier. Found while building/testing the POS rewrite (`auditLog('pos', 'created', ...)` called from inside `execute_pos_sale()`'s transaction). **Fixed at the source**: `ensureTable()` now probes via `SELECT 1 FROM system_audit_log LIMIT 1` first, matching every other `ensure*()` helper's convention — this protects every module that calls `auditLog()`, not just POS. **Lesson**: any code elsewhere in this app that calls `auditLog()`/`auditLogOrder()`/`auditLogExpense()` etc. from inside an open transaction (e.g. `cr/credit_production.php`, `cr/credit_dispatch.php` per the Jul 26 entries above) was exposed to this until this fix — those call sites happened to survive because they were already calling `auditLog()` AFTER `$db->commit()` (verified for credit_dispatch.php/credit_production.php), which is now confirmed to be the *correct* pattern for a different-but-related reason: keep `auditLog()` calls outside transactions as a standing rule, not just to sidestep ENUM issues.
