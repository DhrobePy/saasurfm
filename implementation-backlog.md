- **Two more real bugs hit and fixed while wiring this up**:
  1. tFPDF's `AddFont(..., $uni=true)` needs a `TTFontFile` class from tFPDF's own `ttfonts.php`, which ships with its own `require` commented out (assumes an autoloader) — fixed by requiring it explicitly in `chairman_report_pdf.php`.
  2. Tried registering a cheap fake-italic by pointing style `'I'` at the same Regular TTF already used for style `''` — this silently corrupted BOTH font entries: tFPDF's `AddFont()` derives its on-disk metrics-cache filename from the TTF filename alone (not the family+style key), and its `include()` of that cached `.mtx.php` file overwrites `AddFont()`'s own local `$fontkey` variable in the current scope, so the second `AddFont()` call re-registered under the *first* call's fontkey. ## 🔵 MAJOR NEW INITIATIVE — Loans (related-party cash advances) — BUILT (22 Jul 2026)
**Status: fully built, lint-clean, NOT runtime-tested (no local DB).** Trigger: some customers/suppliers/related parties (e.g. "Tender Business," a sister concern) borrow cash from the company to fund things like tender participation, then repay after the deal closes. Brainstormed with the user first (mirroring the Commodity Trading kickoff pattern), locked 3 answers: (1) borrower must be an existing Customer or Supplier record (no standalone "loan party" concept — simplest, no duplicate contact management); (2) interest-free advances (no accrual engine); (3) disbursement goes through the same maker/checker ৳-limit engine as every other cash-out action.

**Core design decision — loans are a THIRD kind of balance, deliberately NOT posted into `customer_ledger`/`supplier_ledger`:** none of those tables' `transaction_type` ENUM values (`invoice`/`payment`/`advance_payment`/`adjustment`/`credit_note`/`debit_note`/`opening_balance`) honestly describe "we lent you cash" — this session has hit real bugs before from overloading a mismatched ENUM value, so a party's **trading balance** (AR/AP, what they owe for goods) and their **loan balance** (cash advances) stay two separate, clearly-labeled numbers, never merged.

**New module `loans`** (own top-level module in `getModuleRegistry()`, icon `fa-hand-holding-dollar`, color amber, Superadmin/admin default + fully delegable):
- Schema (helpers.php, self-migrating): `loans` (loan_number, `customer_id` OR `supplier_id` — exactly one, principal_amount, amount_repaid, balance_due, loan_date, nullable expected_return_date, purpose, status ENUM(pending_approval/active/closed/rejected), journal_entry_id), `loan_repayments` (repayment_number, loan_id, denormalized customer_id/supplier_id, amount, repayment_date, payment_method, bank_account_id, reference_number, journal_entry_id). `ensureLoanAccounts()` seeds "Loans & Advances Receivable" (1450, Other Current Asset) — GL row only, no schema change (chart_of_accounts already supports that account_type).
- Accounting: disbursement = DR Loans & Advances Receivable / CR Cash-or-Bank (deposit-account resolution pattern reused from `customer_payment.php`, but direction flipped since cash is leaving — bank bridge uses `entry_type='debit'`, confirmed via `BankManager.php`'s `balance = SUM(credit) − SUM(debit)` convention). Repayment reverses it (`entry_type='credit'`).
- `loans/loan.php`: disbursement form with a genuinely NEW pattern — a **combined customer+supplier dynamic search** (single search box, both tables merged client-side, each result tagged Customer/Supplier, business-partner badge shown same as elsewhere). New `loan_disbursement` ৳ limit type (`getLimitBearingActions()`) + new `loanDisbursementApprovalRequiredForAll()` policy toggle (own Settings card, mirrors `commoditySaleApprovalRequiredForAll()` exactly) — deliberately its OWN limit/policy, not reusing `commodity_sale`'s, since lending cash is a different risk profile.
- `loans/repay_loan.php`: collection page. **Deliberate consistency choice**: reuses the SAME `collect_payment` ৳ limit + global `paymentApprovalRequiredForAll()` toggle as every other money-*in* action (commodity payments, customer payments) rather than inventing a third payment policy — avoids a loophole where collecting via Loans bypasses the org's payment-approval stance. Self-healing `balance_due = principal_amount − amount_repaid`; auto-closes the loan (`status='closed'`) once fully repaid.
- `loans/view_loan.php`: detail + disbursement journal + repayment history with per-row Reverse buttons — same layout convention as `view_commodity_sale.php`, minus the Timeline (no edit-chain concept was requested for loans, so no `commodity_sale_edits`-equivalent table was built — loans only have Delete, not Edit, for now. `can_edit` page_action was registered for future use but no edit page exists yet).
- `loans/delete_loan.php` / `loans/delete_loan_repayment.php`: Recycle-Bin-backed reversal, notably SIMPLER than the commodity-sale equivalents since there's no customer_ledger reindexing or inventory to restore — just archive the journal + the row. Loan deletion blocked if `amount_repaid > 0` (reverse repayments first, same precedent as everywhere else).
- `loans/dashboard.php`: outstanding total, overdue-loan alert banner (past `expected_return_date` with balance still due), MTD-style disbursed/repaid tiles, filterable Loan History (date range + party type + specific customer/supplier).
- Wired into `cr/approval_requests.php`: two new request types, `loan_disbursement` (own cap) and `loan_repayment` (reuses `$my_collect_cap`) — amber-colored, review links to `../loans/loan.php?pending_req=` / `../loans/repay_loan.php?pending_req=`.
- `getExceptionRadar()` gained `overdue_loans` + a matching tile on the main admin dashboard (`pending_approvals` already covers loan requests for free, shared `cr_pending_requests` table).
- `cr_pending_requests` limitation noted, not fixed: that table only has a `customer_id` column, no `supplier_id` — a supplier-only loan's pending-request row shows a blank party in the queue's dedicated column, though the `summary` text field always includes the party name regardless, so it's not actually blocked/broken, just a cosmetic gap in one column.
